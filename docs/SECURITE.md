# Revue de sécurité (nov. 2026)

Périmètre : `worker/**`, `src/api/**`, `.github/workflows/**`. Seuls des problèmes concrets, avec un scénario d'attaque.

| Gravité | Fichier:ligne | Problème (scénario) | Correctif | État |
|---|---|---|---|---|
| **Haute** | `worker/index.ts:207` (`PUT /settings/market`), `worker/settings.ts:83` | N'importe quel utilisateur connecté (l'inscription est ouverte) peut remplacer la clé EODHD **de tout le site** et cocher « payant ». Scénario : un inconnu crée un compte via le lien partagé, colle sa propre clé gratuite → la clé payante du propriétaire est écrasée (perdue, les cours de tous passent sur la clé de l'inconnu), ou `paid: true` sur une clé gratuite fait sauter le budget de 20 appels. | Réserver la route au propriétaire du site (ex. secret `ADMIN_EMAILS`, ou premier compte créé) ; refuser `PUT` si une clé est déjà enregistrée et que l'appelant n'est pas admin. | **Corrigé** (seul l'auteur de la clé peut la changer) |
| **Haute** | `.github/workflows/deploy-ami.yml` (job `build`) | Le code du fork (`npm run build`, config Vite, wrangler local de `node_modules`) s'exécutait directement sur le runner, dans le scope de cache de `main`. Avec `sudo`, il peut lire le jeton runtime d'Actions et **empoisonner le cache** (`setup-node cache: npm` de `deploy.yml`, ex. `~/.npm/_npx`), puis exécuter du code dans `deploy.yml` qui détient `CLOUDFLARE_API_TOKEN` → prise de contrôle du compte Cloudflare. | Installation, build et bundle du fork dans un conteneur Docker non privilégié (pas d'accès au runner ni au jeton de cache). | **Corrigé** |
| Moyenne | `worker/google.ts:75` | Pré-prise de contrôle de compte : l'inscription par mot de passe ne vérifie pas l'e-mail. Un attaquant crée un compte avec l'adresse de la victime ; la victime se connecte plus tard avec Google et atterrit dans ce compte, dont l'attaquant connaît le mot de passe → il lit toutes ses données. | À la connexion Google d'un compte à mot de passe : le mot de passe est révoqué (compte Google uniquement) et toutes les sessions existantes sont supprimées. | **Corrigé** |
| Moyenne | `worker/auth.ts` (`login`) | Aucune limite de tentatives : force brute illimitée du mot de passe (minimum 10 caractères seulement), et chaque essai coûte 100 000 itérations PBKDF2. | Max 10 échecs / 15 min par (e-mail, IP `cf-connecting-ip`), compteurs dans `market_cache`, nettoyés à chaque connexion réussie ; HTTP 429 au-delà. | **Corrigé** |
| Moyenne | `worker/index.ts:188` (`/market/history`, `/market/quotes`, `/market/profile`), `worker/market/index.ts:121` | Le budget EODHD (20 appels/jour pour tout le site) est partagé : un seul utilisateur (inscription libre) épuise le quota en demandant 20 tickers inconnus (`?symbols=A1,A2,…`, jusqu'à 80 par requête) → plus de cours pour personne jusqu'au lendemain. | Quota par utilisateur (ex. ≤ 5 nouveaux tickers/jour hors titres déjà en cache ou détenus), ou ne récupérer que les symboles présents dans les transactions de l'utilisateur. | Non corrigé (hors périmètre) |
| Faible | `.github/workflows/deploy-ami.yml` (étape « Copy secrets ») | Le Worker de l'ami reçoit `GOOGLE_CLIENT_ID/SECRET` de Guillaume : le code du fork (non relu) peut lire et exfiltrer le secret client OAuth de Guillaume. | Utiliser des secrets dédiés `AMI_GOOGLE_CLIENT_ID/SECRET` (client OAuth séparé). Non changé pour ne pas casser la connexion Google existante du site ami. | Non corrigé (nécessite de créer des secrets) |
| Faible | `worker/index.ts:135` (`/restore`) | `broker`/`kind` des comptes ne sont pas validés, `manualPrices` sans limite de taille ni contrôle de type (`p > 0` accepte `"5"`), boucle `upsertInstrument` non bornée → données incohérentes ou requête très longue. | Réutiliser la validation de `POST /accounts`, borner les tableaux (comme les 5000 transactions). | Non corrigé (hors périmètre) |

Vérifié sans problème : filtrage `user_id` de toutes les requêtes D1 utilisateur (y compris les mises à jour de transactions et `assertAccount` pour les comptes cibles), sessions (jeton 256 bits, hash SHA-256 en base, cookie HttpOnly/SameSite=Lax), CSRF (vérification d'`Origin`, aucune route GET avec effet de bord hors OAuth protégé par `state`), redirections (toujours relatives), pas de `dangerouslySetInnerHTML` dans `src/`, `login_error` affiché comme texte React, jetons IBKR chiffrés AES-GCM, config Wrangler du site ami générée (le fork ne peut pas lier d'autres Workers/bases).
